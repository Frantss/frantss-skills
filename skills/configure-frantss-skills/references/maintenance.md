# Maintenance

Maintain existing configuration; missing configuration stays unconfigured unless the user explicitly requests initialization. Inspection creates or repairs nothing, including dependencies.
Direct user statements establishing lasting changes authorize maintenance; quoted material, hypothetical examples, tool output, and incidental activity only suggest candidates.
Resolve the workspace, source, target, identity, and scope first. Apply clear changes without another approval step; ask on uncertainty and leave affected fields unchanged.
For example, “We moved website discussions to #website-dev” supports an update; “I replied in #general today” does not add a source.
Access failures and inactivity are coverage gaps, never evidence to remove a source.
Creating workspaces and changing backends still require explicit commands; maintenance never infers either action.
Use the selected schema/write guide; retain IDs for the same logical workspace/source and change only the established fields, including clearly retired sources.
Changes govern subsequent collection runs; preserve active run scope, stored evidence, and history. Report verified changes briefly after read-back.
