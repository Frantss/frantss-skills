# Sandboxed CLI access

The CLI communicates with the desktop app; sandbox isolation can report "unable to find Obsidian" while the app is running. On app-discovery/IPC failures or sandbox denials, retry the read-only `obsidian help` check once outside the sandbox before declaring CLI access unavailable. Inspect error text even when the exit code is zero.
In [Codex](https://learn.chatgpt.com/docs/security), when the execution tool supports escalation, request `sandbox_permissions: "require_escalated"` with an Obsidian-specific justification. In [Claude Code](https://code.claude.com/docs/en/sandboxing#the-unsandboxed-retry-escape-hatch), when Bash exposes it, use `dangerouslyDisableSandbox: true` through the normal permission flow. These are tool arguments, not Obsidian flags; keep host approvals and sandbox policy intact.
If the outside-sandbox check succeeds, use that execution mode for subsequent Obsidian calls in this session, preserving vault selection and per-call permissions. When this restriction is already established, start in that mode. If escalation is unavailable/denied or the retry fails, stop and report the exact unresolved access requirement; preserve unsaved payloads.
Before retrying a write with an uncertain outcome, inspect notes and retained revisions through the working CLI and follow [write recovery](writes.md); repeat only missing operations with the same identities.
