02 / Inputs, outputs, and example requests

Use the skill that fits the gap.

Explicit skill names make intent clear. Automatic selection is also enabled. These example prompts describe requests; they do not run commands.

break-downCollect and explain software or a specification.

Use when

You need a structured understanding of existing software or a complete or partial specification. It also accepts scoped analysis requests from discovery.

Delivers

Areas, rules, states, cases, evidence, conflicts, and gaps. It includes interfaces, data, background behavior, and stated nonfunctional constraints beyond journeys.

Important boundary

Preserve whether requirements are proposed or agreed. Separate observed results, code inferences, and derived cases. Analysis leaves unsupported outcomes open.

Completion

Every in-scope source requirement maps to an area and cases or an explicit gap. Reconstructed maps name inspected and unexplored surfaces.

Example request

Use $break-down to collect and explain the invitation specification, including permissions, API rules, expiry jobs, states, and stated latency targets. Keep missing decisions open.
Source: break-down/SKILL.md
frame-problemEstablish the need, evidence, and outcome.

Use when

The problem, intended outcome, scope, or constraints are unclear. A proposed solution can be an input without becoming an agreed direction.

Delivers

A problem brief covering context, people, goals, evidence, boundaries, constraints, and consequential questions.

Important boundary

Separate needs from symptoms, assumptions, and proposed solutions. Preserve prior agreements and leave unknown baselines or targets explicit.

Completion

Each in-scope need and constraint is accounted for. Evidence gaps and blockers to the brief's intended use are identified.

Example request

Use $frame-problem to understand why invitations fail to produce completed onboarding. Define the problem and useful success criteria before choosing a solution.
Source: frame-problem/SKILL.md
design-solutionChoose an approach and define cooperating parts.

Use when

You need to compare solutions, refine a design, or plan a technical migration. Supplied requirements or an existing design are sufficient starting points.

Delivers

A scoped proposal with alternatives, responsibilities, interfaces, dependencies, trade-offs, and unresolved choices. Migration sequencing is included when requested.

Important boundary

Concept selection can happen before detailed behavior discovery. Keep proposed approaches separate from decisions and verify feasibility against relevant code or authoritative sources.

Completion

The design addresses the supplied needs, behavior, and constraints at the requested depth. Unverified assumptions and unresolved decisions are visible.

Example request

Use $design-solution to compare ways to resend invitations. Define responsibilities, interfaces, dependencies, verification, and risks. Keep this request to the proposal.
Source: design-solution/SKILL.md
discover-behaviorResolve expected behavior through conversation.

Use when

Consumer-visible rules, boundaries, or outcomes need agreement. Consumers include people, API clients, and calling code.

Delivers

Rules and examples with starting conditions, events, outcomes, side effects, and prohibited effects. Agreements, proposals, evidence, and open decisions remain distinct.

Important boundary

Check relevant revisions before reusing observations or code inferences. Refresh affected findings without changing agreements. Use break-down for missing context, then focus discovery on unresolved outcomes and affected interactions.

Completion

Coverage, interactions, contradictions, and gaps are reviewed. Unresolved choices block only dependent work; silence does not settle a decision.

Example request

Use $discover-behavior to agree invitation resend rules. Analyze the supplied specification where needed, then discuss eligibility, expiry changes, and limits.
Source: discover-behavior/SKILL.md
formulate-behaviorTurn agreed behavior into source-linked Gherkin.

Use when

The expected behavior is settled and Gherkin is requested or fits existing project tooling. Precise native acceptance cases can go directly to slicing or implementation.

Delivers

Independently understandable scenarios, Rule groups, and Scenario Outlines where useful. Preserve project tags, terminology, units, case identities, and source mappings.

Important boundary

Derive only outcomes supported by agreed rules. Valid Gherkin syntax does not establish that software behaves correctly.

Completion

Every in-scope rule and example is accounted for, with conflicts and gaps explicit. Report parser validation or manual syntax review separately from runtime testing.

Example request

Use $formulate-behavior for these agreed rules: integer inputs 1 through 5 pass; other integers fail without changing state. Preserve our existing tags and case-ID comments.
Source: formulate-behavior/SKILL.md
slice-workGroup agreed behavior into verifiable tickets.

Use when

You need bounded implementation outcomes and dependencies from an agreed behavioral specification. Gherkin is optional.

Delivers

Tickets with stable IDs, outcome titles, context, dependencies, and behavior mappings. Add verification guidance where setup or regressions need explanation.

Important boundary

Each selected case has one completing owner, is already satisfied with evidence, or remains an explicit gap. Regression references preserve ownership. One ticket can cover the whole selected scope.

Completion

Coverage is accounted for, dependencies are acyclic, prerequisites are verifiable, and ticket sources resolve. Drafting tickets does not itself authorize publication or implementation.

Example request

Use $slice-work to draft tickets from these agreed invitation cases. Choose useful boundaries and dependencies. Do not publish or implement them.
Source: slice-work/SKILL.md
implement-ticketImplement and verify one authorized outcome.

Use when

A ticket or named implementation scope has clear acceptance cases and implementation is authorized. Ticket documents, prior BDD stages, and Gherkin are optional.

Delivers

Code, native tests, and current evidence for all promised cases. Default to test-first, while reporting a concrete reason when that ordering is impractical.

Important boundary

Verify real prerequisites and the baseline. If adequate passing evidence already covers every case, report that no code change is needed. Ask only about consequential missing scope or behavior.

Completion

All promised behavior and required checks pass on the final code, with no missing coverage or unresolved blocker. Record failed, blocked, and unexecuted checks accurately.

Example request

Use $implement-ticket to implement TK-001 from its supplied acceptance cases. Use the existing native tests and report verification against the final code.
Source: implement-ticket/SKILL.md
03 / Analysis supports agreement

Breakdown gives discovery a starting point.

The two skills share behavioral concepts. They answer different questions and preserve different kinds of certainty.

discover-behavior

Identify a consequential behavior choice. Reuse sufficient context, or request analysis of the specific missing area.

Sends: subject, sources, scope, and gaps.

⇄

break-down

Collect a supported map of rules, states, cases, interfaces, and stated constraints. Explain conflicts and unknowns.

Returns: findings, source identities, evidence, and gaps.

Works with a specification alone

There does not need to be an application to inspect. A proposed specification can be mapped, with its proposed status preserved. Missing rules remain questions for discovery.

Can repeat within a conversation

A later decision can expose another factual gap. Request a focused breakdown and keep unaffected findings. Check revisions before reuse; refresh stale observations without silently changing agreements. Discovery also works without break-down.

An explanation establishes what the sources support. A behavior decision establishes what is expected.

Sources: break-down and discover-behavior.

04 / Choose how work is kept

Standalone by default. Tracked when requested.

These are working modes, not extra stages. An unrelated BDD folder does not enroll a new request into that run.

Use the supplied inputs and return the requested result.

Work in the conversation or requested document. Earlier skills, Gherkin, and a new BDD folder are not general prerequisites.

How a tracked run is organized

Use .scratch/bdd/<feature_slug>-<NNN>/, with a stable feature slug and a three-digit per-feature ordinal. Create only records for participating stages.

Illustrative YAML. The active stage can be framing, concept, design, discovery, formulation, slicing, or implementation.

Run sections

Documents keeps named slice entries, scope, file-qualified members, dependencies, and a File | Status table.

Validation keeps evidence and limitations. Implementation adds ticket execution and behavior-check tables.

Next action identifies the current step. Preserve identities, human edits, and unaffected work when resuming.

pending: unvisiteddraft: incompleteblocked: unresolved prerequisiteready: sufficient for intended usepartial: named usable scope and blockers

Document readiness differs from implementation completion. Implementation states are pending, in_progress, blocked, and done; behavior-check results are passed, failed, blocked, and not_run. Changes that invalidate evidence reset affected checks and reopen affected done tickets.

break-down has no separate BDD stage or fixed tracked-file schema. It returns its map to the caller or saves it only when requested or continuing an identified record.

05 / Know what each result proves

Keep evidence and agreement distinct.

A source reference establishes where a claim came from. An executed assertion establishes a checked outcome within its tested scope.

Illustrative invitation example. These rows explain the contracts; they are not results from an executed invitation system.
Kind of resultExampleWhat it establishes
Source statementA proposed specification says invitations expire after seven days.The proposal contains that rule. Its presence alone does not establish agreement or implementation.
Implementation inferenceReading an expiry condition suggests rejection at the cutoff.A source-backed inference. No runtime observation has been made.
Agreed behaviorAcceptance at or after expiry must fail without creating membership.An expected outcome accepted during discovery or supplied as an agreed requirement.
Formulated scenarioGiven a pending invitation at expiry, when accepted, then reject it and create no membership.A concrete specification of the rule. Parsing it checks syntax, not system behavior.
Executed checkA native test asserts rejection and no membership at the cutoff, then passes on the final code.Evidence for that acceptance case on the checked code. Other cases and required regressions still need coverage.

Traceability runs from source rules to cases, ticket ownership, and native assertions. Keep one authoritative definition of each rule and preserve its identity across handoffs.

  • Missing decisions stay open.

    Infer only outcomes supported by supplied rules. Unanswered questions block dependent work, not an unrelated settled subset.

  • Scope does not imply permission.

    Explaining behavior does not authorize changes. Drafting tickets does not authorize publishing them. Continue implementation only when it is included in the request or prior authorization.

  • Prepared inputs let you enter later.

    Clear native acceptance cases can go straight to implementation without a ticket document. Add Gherkin when requested or useful, and slicing when implementation boundaries need work.

  • Ordinary work can stay ordinary.

    A typo correction or a request to run existing tests does not require BDD discovery, formulation, or new run records.
